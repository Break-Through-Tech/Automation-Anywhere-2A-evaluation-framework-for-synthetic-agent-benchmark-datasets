# Required-path clarification — draft

Status: proposed development probe; not active in the published scoring protocol.
Purpose: clarify existing required-work and selected-branch rules, with unchanged
five dimensions, 20% weights, anchors, evidence rules and numeric formula.

## Proposed prompt addendum

Count work needed along a source-supported, policy-compliant sufficient path to the
intended valid endpoint. An escalation, refusal or cancellation can be that endpoint.
Include necessary discovery, identity checks, applicable prerequisites, user guidance
and any recovery needed to establish the exit condition. Judge-only initial records
are not knowledge available to the task agent. Do not assume an oracle identifies the
exit immediately or prescribe a unique shortest tool sequence when sources do not.

Once a decisive mandatory exit is established, do not charge additional repairs,
payment processing, approvals or investigations on branches that no longer need to
be completed. Include further work only if sources independently require it before
that exit, and cite the requirement. Multiple seeded faults do not automatically
make every repair necessary. Setup operations themselves remain excluded.

In the existing workload and dependency rationales, identify the decisive exit,
necessary work before discovery, and work excluded afterward. If several diagnostic
orders are defensible, explain the chosen sufficient path and uncertainty. If policy
requirements conflict, flag the conflict rather than silently combining all paths.
Do not change a score merely because an earlier case scored differently. No prior
score, review judgment, task label or desired score is supplied in this probe.

## Interpretation and limits

This is a generic clarification, not a telecom-only scoring rule. It does not assert
that every escalation is easy. Discovery, authentication, user behavior and required
handoff preparation can still be difficult. The technical manual's specific locked-SIM
instruction and its general best-effort rule both matter; this review is not an
independent human label or proof of a correct replacement numeric score.

The private SIM-status helper shows that a missing card masks its locked status until
reseating. That static code is useful review evidence but was not fully supplied to
the original judge. It is NOT added to this probe's input: changing prompt and context
at the same time would confound the comparison. A later context-sensitivity test can
be separate if needed.

## Bounded proposed test

Four previously inspected development cases: two whose saved dependency explanations
explicitly include a payment/resumption chain, and two contrast cases that explicitly
exclude that chain after the locked-SIM exit. One judgment each, same frozen inputs,
evidence schema, gpt-6-sol / low reasoning / 10000 output-token cap. Only the system
prompt addendum changes. Stop on the first API, schema, evidence or identity error.
No automatic retries, full-dataset rerun, rescoring of published means or pooling
with the old protocol. Four calls would be a development check, not calibration or
independent accuracy validation; repeatability remains a later separate decision.

No API calls are authorized or made by preparing this plan.
